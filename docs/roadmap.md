# VisionQL Roadmap

> 阶段以能力集定义,不承诺日历时间——顺序与依赖是承诺,日期随设计伙伴反馈滚动确定。各项能力的详细定义见 [PRD](./prd.md) 与各设计文档,此处只维护"什么时候做、为什么是这个顺序"。

## 主线:每个版本退役一个最大风险

排序不按功能清单,按假设的风险从大到小——上一个假设不成立,下一个版本的投入就是浪费:

| 阶段 | 回答的问题(退役的风险) | 一句话目标 | 状态 |
|---|---|---|---|
| **v0.1(MVP)** | 核心抽象是否成立——有人愿意用 SQL 查视频吗 | `pip install` 后一条 SQL 跑通批与流;零外部依赖 5 分钟出首个结果 | 设计评审中 |
| **v0.2** | 能否托付生产——流查询 7×24 可运维,分析师与 Agent 能否经标准协议进入 | 服务态常驻;Flight SQL 打开客户端生态,Workbench 与 MCP 首发 | 规划中 |
| **v0.3** | 护城河是否兑现——"声明式省 GPU 钱"可测量、可被用户看见 | 优化器把 GPU 成本降一个量级,并让用户看见省在哪 | 规划中 |
| **v1.0** | 能否规模化与商业化——多租户隔离与兼容承诺 | 集群、多租户、稳定性承诺,企业版就绪 | 规划中 |
| **v1.x+** | 边缘协同的自动化 | 边缘/中心从手动分工(v0.2 起可用)走向自动切分与车队规模化 | 远期 |

## 决策点(带截止时机的未决项)

未决项不挂在"待定"里漂着——每项有最迟决策时机与解锁对象:

| 决策 | 最迟何时定 | 解锁什么 | 当前状态 |
|---|---|---|---|
| 楔子场景二选一(安防/园区 vs 内容审核) | v0.1 收尾前(设计伙伴访谈驱动) | v0.2 场景包方向;`TRACK` 档位(安防则升 P0);首发连接器投入 | 未定(PRD 开放问题 1) |
| 开源发布时点(随 v0.1 还是 v0.2) | v0.1 收尾前 | 社区冷启动与设计伙伴节奏;成功指标"开源后 90 天"的起算点 | 未定 |
| `IMAGE` 列客户端协议表示 | v0.2 Flight SQL schema 定稿前 | Flight SQL 前端、Workbench、BI 直连 | 已有倾向:默认引用 + `thumbnail` 会话选项 + `FRAME_AT` 点查(Workbench 已按此先行设计,PRD 开放问题 5) |
| 跨流 JOIN(ReID 轨迹)归属 v0.3 还是 v1.x | v0.3 规划前 | v0.3 范围;对安防场景的深度承诺 | 未定(PRD 开放问题 4) |

## v0.1(MVP)——单机端到端可用

**退役的风险**:核心抽象(帧的关系表、MODEL/FUNCTION 分层、TUMBLE 双模)是否成立;声明式接口是否真把典型任务降到 30 行内;第一次接触是否足够轻(激活)。

仅 engine,无 workbench:

- 多模态类型系统(IMAGE/VIDEO/BOX2D/VECTOR)
- 批:图片/视频目录表、`FRAMES()`、`UNNEST`
- 流:RTSP 单流 + TUMBLE 窗口(尽力而为投递)
- 模型/函数注册(检测、嵌入两类)+ Python UDF(库态)
- Sink:Kafka、Parquet/Lance、Console(调试)
- 库态 + shell + DataFrame API + `visionql run`
- 基础优化:推理提取、列裁剪、帧采样下推、时间谓词下推

**验收**(PRD 第 4 节两场景,合并覆盖全部 MVP 组件):

- **场景 A(批流一体)**:同一条"每分钟人数入 Kafka"SQL 在 RTSP 流与历史视频表两种模式下运行且结果一致;典型任务 < 30 行代码、< 30 分钟上线;
- **场景 B(零依赖首触)**:本地图片目录 → Python UDF 过滤 → 嵌入 → 写 Lance → 以文搜图;`pip install` 到首个结果 ≤ 5 分钟,零外部服务(TTFV 指标)。

## v0.2——流查询生产化

**退役的风险**:流查询能否 7×24 托付生产;标准协议(Flight SQL)之上能否长出真实的客户端生态——分析师(Workbench)、Agent(MCP)、BI(JDBC/ADBC)三类入口。

交付分两档,P1 滑落至 v0.2.x 不阻塞发布(服务态是头号项)。

**P0(发布门槛)**:

- 服务态 `visionqld`:常驻进程、查询管理(状态/暂停/恢复、崩溃自愈)
- Arrow Flight SQL 前端,含 TLS、认证、表/流级权限
- Kafka 帧源(可重放源,至少一次投递)
- Workbench 首发:SQL 编辑与执行、多模态结果预览(缩略图/检测框叠加)、流结果实时预览、目录浏览、持续查询运维、成本面板(实测口径);引擎配套两项:结果集缩略图会话选项、按引用取帧函数
- MCP 服务器(Agent 工具接入):Flight SQL 之上的薄适配层,实现成本低;打开 PRD 用户 4(Agent 开发者)的整条采用通道——与 Workbench 同属"客户端生态"档且 PRD 第 5 节列为 v0.2 关键交付,故归 P0 而非搭车项
- Prometheus 指标端点

**P1(搭车项,可滑落)**:`TRACK` 跨帧跟踪、`HOP`/`SESSION` 窗口、物化视图维护、Python UDF 进程外 worker、GPU 池化与显存管理、Webhook 告警 Sink。若楔子场景定为安防/园区,`TRACK` 提升为 P0。

**生态(与设计伙伴并行共建)**:首个场景包(模型 + SQL 模板 + 面板),方向随楔子场景决策点。

**验收**(可控的能力口径,不含外部依赖):7×24 soak 与强杀恢复演练(Kafka 源不丢未关闭窗口的贡献);分析师经 Workbench 完成"零安装可查"旅程;Agent 经 MCP 完成一次"自然语言 → SQL → 画面答案"问答。设计伙伴进入生产流量是目标,不是发布门槛。

## v0.3——智能降本

**退役的风险**:"声明式引擎省 GPU 钱"这条最深护城河是否真实兑现且可被用户看见——商业化定价锚点(按 GPU 时长计价,与客户利益同向)的前提。排在 v0.2 之后不是因为不重要,而是 7×24 常驻是设计伙伴产生真实 GPU 账单的前提——没有账单,省钱无从验证。

- 模型级联优化器(小模型过滤 + 大模型确认)
- 推理结果物化与跨查询复用
- 向量索引(接 Lance 原生索引,与物化配套——暴力 TopK 检索自 v0.1 可用,本项按数据规模/场景需求触发,无需求可继续后移)
- VLM 谓词(VQA 模型类型激活)
- `EXPLAIN` 成本预估(GPU 时长/费用)
- 聚合粒度反推采样率、空间 ROI 裁剪
- workbench:成本面板叠加预估可视化;候选:视频时间轴预览
- 跨流 JOIN(ReID 轨迹):是否入本版见决策点表

**验收**:在采样无法覆盖的全帧负载上(如逐帧内容审核),GPU 时长相对逐帧全量推理基线下降 ≥ 5x——可采样负载的 5x 已由 v0.1 采样下推兑现,不计入本阶段。

## v1.0——规模化

**退役的风险**:多租户下的隔离、配额与跨版本兼容承诺——企业版收费与被平台团队采购的前提。

- 集群态(计算与模型服务独立扩缩)
- 精确一次投递(检查点 + 事务 Sink)
- 多租户治理:配额、资源组、审计日志
- WASM UDF(用户代码沙箱与边缘分发)
- SQL 方言与目录格式的语义化版本承诺生效
- workbench:权限/审计界面呈现、保存查询的服务端存储与团队共享

**验收**:多租户配额与隔离压测;跨版本升级演练(兼容承诺的首次兑现)。

## v1.x+——边缘协同

手动边缘部署不是本阶段交付——同一 `visionqld` 二进制(含 ARM)随 v0.2 服务态即可跑在边缘盒上,就地解码/检测、只回传结构化结果。本阶段做"自动"与"规模":

- 同一条查询的边缘/中心执行段自动切分
- 边缘节点车队管理(企业版能力)
- 边缘 NPU 推理后端
- Workbench 多端点(边缘车队)接入
- 候选:历史回填 + 实时接续——同一查询先回扫录像再无缝接 live(PRD 开放问题 6),随设计伙伴需求强度决定

## 排序逻辑备忘

- 服务态是一切生产化的闸门,Flight SQL、Workbench、MCP、BI 直连全部挂在它之后;
- v0.1 就把推理孤立为显式计划节点,v0.3 的级联/缓存/成本核算全部长在这个白盒上——先有白盒,后有降本;
- 投递语义按源分档递进:尽力而为(RTSP)→ 至少一次(Kafka 源)→ 精确一次(v1.0),每档只做当期源支撑得起的承诺;
- Workbench 只依赖 Flight SQL 协议,首发后独立发布,不跟引擎内部走。
