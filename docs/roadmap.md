# VisionQL Roadmap

> VisionQL 的版本阶段按能力划分，不承诺具体发布日期。版本顺序和依赖关系相对稳定，时间安排会根据设计伙伴的反馈动态调整。各项能力的详细定义见 [PRD](./prd.md) 和相关设计文档；本文只说明每个阶段做什么，以及为什么按这个顺序推进。

## 主线：按风险安排版本顺序

每个版本都优先验证当前最关键的产品或工程假设。如果这一阶段的假设不成立，就不会贸然投入下一阶段。

| 阶段 | 需要回答的问题 | 一句话目标 | 状态 |
|---|---|---|---|
| **v0.1（MVP）** | 用户是否愿意用 SQL 查询视频，核心抽象是否成立 | `pip install` 后即可用一条 SQL 跑通批处理和流处理；不依赖外部服务，5 分钟内得到第一个结果 | 设计评审中 |
| **v0.2** | 流查询能否稳定运行在生产环境中；分析师和 Agent 能否通过标准协议使用 VisionQL | 提供可常驻运行的服务；通过 Flight SQL 接入 Workbench、MCP 和其他客户端 | 规划中 |
| **v0.3** | 声明式优化能否显著降低 GPU 成本，并让用户清楚看到优化效果 | 将典型负载的 GPU 成本降低一个数量级，并解释成本节省来自哪里 | 规划中 |
| **v1.0** | 系统能否在多租户环境中稳定扩展，并提供明确的兼容性承诺 | 支持集群和多租户，达到企业生产环境的要求 | 规划中 |
| **v1.x+** | 边缘和中心之间的任务分配能否自动化 | 从手动部署到边缘，逐步演进为自动切分和大规模边缘节点管理 | 远期 |

## 需要按时做出的决策

以下问题尚未定论，但每一项都有明确的决策时间，避免长期悬而不决。

| 决策 | 最迟决策时间 | 影响范围 | 当前状态 |
|---|---|---|---|
| 首个重点场景选择：安防/园区或内容审核 | v0.1 收尾前，由设计伙伴访谈结果决定 | v0.2 场景包方向、`TRACK` 的优先级和首批连接器投入 | 未定（PRD 开放问题 1） |
| 开源发布时间：随 v0.1 或 v0.2 发布 | v0.1 收尾前 | 社区启动节奏，以及“开源后 90 天”成功指标的起算时间 | 未定 |
| `IMAGE` 列在客户端协议中的表示方式 | v0.2 Flight SQL schema 定稿前 | Flight SQL 前端、Workbench 和 BI 客户端 | 初步方案：默认返回引用；通过 `thumbnail` 会话选项返回缩略图；使用 `FRAME_AT` 按需取帧。Workbench 已按此方案设计，详见 PRD 开放问题 5 |
| 跨流 JOIN（ReID 轨迹）安排在 v0.3 还是 v1.x | v0.3 规划前 | v0.3 的范围，以及安防场景的能力深度 | 未定（PRD 开放问题 4） |

## v0.1（MVP）：单机端到端可用

本阶段要验证三件事：帧关系表、MODEL/FUNCTION 分层和 TUMBLE 双模等核心抽象是否合理；声明式接口能否将典型任务控制在 30 行以内；首次使用是否足够简单。

v0.1 只交付引擎，不包含 Workbench：

- 多模态类型系统（IMAGE、VIDEO、BOX2D、VECTOR）
- 批处理：图片/视频目录表、`FRAMES()`、`UNNEST`
- 流处理：单路 RTSP + TUMBLE 窗口（尽力而为投递）
- 模型与函数注册（检测、嵌入）以及库态 Python UDF
- Sink：Kafka、Parquet/Lance、Console（调试）
- 库态、shell、DataFrame API 和 `visionql run`
- 基础优化：推理提取、列裁剪、帧采样下推和时间谓词下推

验收使用 PRD 第 4 节中的两个场景，合并覆盖全部 MVP 组件：

- **场景 A（批流一体）**：同一条“每分钟人数写入 Kafka”的 SQL 分别运行在 RTSP 流和历史视频表上，并得到一致的结果。典型任务少于 30 行代码，从零到上线少于 30 分钟。
- **场景 B（首次使用无需外部服务）**：处理流程为“本地图片目录 → Python UDF 过滤 → 嵌入 → 写入 Lance → 以文搜图”。从 `pip install` 到第一个结果不超过 5 分钟，全程不依赖外部服务（TTFV 指标）。

## v0.2：让流查询可用于生产

本阶段重点验证两点：流查询能否稳定运行 7×24 小时，以及 Flight SQL 能否支撑真实的客户端生态，包括 Workbench、MCP 和 BI 客户端。

交付分为 P0 和 P1。P0 是发布门槛；P1 可以顺延到 v0.2.x，不影响 v0.2 发布。

**P0（发布门槛）**：

- 服务态 `visionqld`：常驻进程、查询状态管理、暂停/恢复和崩溃自愈
- Arrow Flight SQL 前端，包括 TLS、认证和表/流级权限
- Kafka 帧源：支持重放，提供至少一次投递语义
- Workbench 首发：SQL 编辑与执行、多模态结果预览（缩略图和检测框叠加）、实时流结果预览、目录浏览、持续查询运维，以及基于实测数据的成本面板。引擎同时提供结果集缩略图会话选项和按引用取帧函数
- MCP 服务器：在 Flight SQL 之上提供轻量适配，让 Agent 可以调用 VisionQL。它与 Workbench 一样属于 v0.2 客户端生态的核心入口，因此列为 P0
- Prometheus 指标端点

**P1（可顺延）**：`TRACK` 跨帧跟踪、`HOP`/`SESSION` 窗口、物化视图维护、进程外 Python UDF worker、GPU 池化与显存管理，以及 Webhook 告警 Sink。如果首个重点场景选择安防/园区，`TRACK` 提升为 P0。

首个场景包（模型、SQL 模板和面板）将与设计伙伴共同开发，具体方向由重点场景的选择决定。

验收范围限定为系统自身可控的能力：完成 7×24 小时稳定性测试和强制终止后的恢复演练；Kafka 源中尚未关闭窗口的数据贡献不能丢失；分析师可通过 Workbench 完成无需本地安装的查询流程；Agent 可通过 MCP 完成一次“自然语言 → SQL → 画面结果”的问答。设计伙伴是否开始承载生产流量是阶段目标，但不作为发布门槛。

## v0.3：用优化能力降低 GPU 成本

本阶段要验证声明式查询是否能在真实负载中显著节省 GPU，并让用户理解成本是如何降低的。这也是按 GPU 时长计价能否成立的前提。之所以安排在 v0.2 之后，是因为只有持续查询稳定运行后，才能获得可信的生产负载和成本数据。

- 模型级联优化（小模型过滤，大模型确认）
- 推理结果物化和跨查询复用
- 向量索引：复用 Lance 原生索引，并与物化能力配套。v0.1 已支持暴力 TopK 检索；是否在本阶段启用索引取决于实际数据规模和场景需求
- VLM 谓词（启用 VQA 模型类型）
- `EXPLAIN` 成本预估（GPU 时长和费用）
- 根据聚合粒度自动调整采样率，以及空间 ROI 裁剪
- Workbench：成本面板增加预估结果；视频时间轴预览作为候选能力
- 跨流 JOIN（ReID 轨迹）：是否纳入本阶段由前述决策确定

验收标准：在无法通过采样降低工作量的全帧负载上，例如逐帧内容审核，GPU 时长相对逐帧全量推理基线降低至少 5 倍。可采样负载已经在 v0.1 通过采样下推获得收益，不计入本阶段指标。

## v1.0：支持规模化部署

本阶段重点验证多租户环境下的隔离、配额和跨版本兼容能力，使 VisionQL 达到企业采购和付费使用的要求。

- 集群态：计算和模型服务可以独立扩缩容
- 精确一次投递：检查点与事务 Sink
- 多租户治理：配额、资源组和审计日志
- WASM UDF：用于用户代码隔离和边缘分发
- SQL 方言和目录格式开始提供语义化版本兼容承诺
- Workbench：展示权限和审计信息；支持查询的服务端保存与团队共享

验收标准：完成多租户配额与隔离压测，以及跨版本升级演练。

## v1.x+：边缘协同

手动边缘部署不需要等到这一阶段。同一个 `visionqld` 二进制（包括 ARM 版本）从 v0.2 起即可运行在边缘设备上，就地完成解码和检测，只把结构化结果发送到中心。本阶段新增的是自动化和大规模管理能力：

- 自动拆分同一条查询在边缘和中心的执行部分
- 边缘节点集群管理（企业版能力）
- 边缘 NPU 推理后端
- Workbench 支持连接多个端点和边缘节点集群
- 候选能力：历史回填后无缝接入实时流。是否实现取决于设计伙伴的需求，详见 PRD 开放问题 6

## 排序依据

- 服务态是生产化能力的基础。Flight SQL、Workbench、MCP 和 BI 客户端都依赖它。
- v0.1 会先将推理表示为显式计划节点。v0.3 的模型级联、缓存和成本核算都建立在这一基础上。
- 投递语义按数据源能力逐步增强：RTSP 提供尽力而为；Kafka 源提供至少一次；v1.0 再提供精确一次。每个阶段只承诺当前数据源能够支持的语义。
- Workbench 只依赖 Flight SQL。首发后可以独立发布，不需要与引擎内部版本同步演进。
